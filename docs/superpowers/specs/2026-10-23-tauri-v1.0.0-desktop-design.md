# Tauri port becomes the desktop app (v1.0.0) - design

Date: 2026-10-23 (author's answers: 2026-10-24)
Status: approved by the author 2026-10-24 - all questions answered
(section 6), including the derived Linux auto-update one.

## 1. Intent

The Tauri port in `spike-tauri/` replaces the Avalonia/.NET desktop app in
`desktop/OpenDrop/`. The author validated the port live (tray, one window
per machine, integrated title bar, round icon, theme glyphs fixed) and
calls it stable: the next release is **v1.0.0**, skipping 0.17. Old tags
and releases stay Avalonia; from v1.0.0 on, the desktop app is Tauri.

This change restructures the repo, hardens the port where the author
found the parity gaps, updates packaging and CI (Windows **and** Linux),
and rewrites every doc that still describes an Avalonia/.NET world.
Nothing is committed until the author orders it.

## 2. Goals

- `spike-tauri/` becomes `desktop/`; the Avalonia app and its xUnit tests
  leave the repo.
- The app identifies as OpenDrop everywhere (name, exe, version 1.0.0,
  identifier, User-Agent) - no `Spike` left in anything user-visible.
- **Parity with the Avalonia app is complete on the four points the
  author chose to close now**: engine spawn on installed builds, update
  digest verification, a Linux desktop build, and the WhatsNew popup.
- Windows installer, portable zip, Linux tarball and the in-app updater
  keep working.
- CI builds the Tauri app on Windows **and** Linux; Dependabot watches
  npm and cargo instead of nuget.
- README, CONTRIBUTING, SECURITY.md and CHANGELOG describe the Tauri
  reality truthfully, with the **screenshots retaken from the Tauri app**.

## 3. Non-goals / anti-goals

- No Linux distribution packaging beyond the existing tarball (no deb,
  no flatpak, no AppImage).
- No new app features beyond the WhatsNew port and the two parity fixes.
- No rewrite of `docs/superpowers/` history, no rewrite of CHANGELOG
  history (old entries mention Avalonia on purpose).
- No touching `bot.py`, `opensourceui/` (separate repo), the engine's
  behaviour, or the author's running services.
- No commit/tag/push without an explicit order.

## 4. Constraints

- Code, comments and repo docs in English; UI strings FR+EN via
  `src/strings.ts`.
- Never click the author's windows: verification through UIA reads/invokes
  only, never moving his cursor, never killing `python.exe bot.py`, engine
  state decided by the author alone.
- The desktop app spawns the engine (`python -m opendrop.main --headless
  --port`), and `reap_orphan()` kills stray engines at boot: every restart
  of the app cuts the engine, which then restarts itself.

### B. Engine spawn resolution (author: fix now)

`main.rs:207` runs bare `Command::new("python")` with no interpreter
search, no `PYTHONPATH`, no working directory, while the Avalonia
`ServerManager.cs:62-112` resolved the project root, set
`PYTHONPATH=<root>/src` and preferred `<root>/venv/Scripts/python.exe`
(`venv/bin/python3`, `venv/bin/python` on Linux) before falling back to
PATH `python3`/`python`. On an installed build (bundle: `src/` + a `venv`
built from the bundled wheels, no editable install) bare `python` cannot
`import opendrop`, so the engine would never start on a clean machine.

- Port that resolution into `try_spawn`: candidates in order (venv
  Windows, venv Unix python3, venv Unix python, then PATH `python3`/
  `python` as the OS dictates), `PYTHONPATH=<root>/src` prepended to any
  existing value, working directory = project root.
- Project root resolution: the installed app's root is the exe's folder;
  the dev build walks up to the `pyproject.toml` (as Avalonia did).
- Add an installed-app smoke test (launch the installed exe, assert the
  engine answers on 8080).

### C. Update digest verification (author: fix now)

`check_updates_impl` (`main.rs:1051`) picks the first `.exe`/`.msi`
asset and streams it to `%TEMP%\opendrop-update-<tag>.<ext>`; nothing
hashes it before `runas` elevation executes it, while SECURITY.md
promised exactly that check and the Avalonia `UpdateService` refused
releases without a digest.

- Read the asset `digest` field from the same API response
  (`"sha256:<hex>"`), hash the completed download with the `sha2` crate,
  and on mismatch delete the file, abort and surface the error in the
  update toast (same behaviour as Avalonia's `Up.NoDigest`).
- Releases without a digest are refused too (Avalonia behaviour).
- Resume interaction: hash once the `.part` reaches its final name, so a
  resumed download is always verified before execution.
- The tag format check comes back as well: only `vX.Y.Z` is accepted
  (the current code strips a leading `v` and accepts anything).
- **Linux parity (author: port it)**: on Linux the updater picks the
  `.tar.gz` asset instead of the setup, verifies its digest the same
  way, extracts it, and re-runs the bundle's `install.sh` through
  `pkexec` so `/opt/opendrop` is upgraded in place - the Avalonia
  `UpdateRunner` flow. `~/.opendrop` and the receive/share folders are
  never touched.

### D. Linux desktop build (author: build it)

- `desktop.yml` keeps both legs: Windows + `ubuntu-latest`, with the
  Ubuntu job installing the Tauri Linux prerequisites
  (`libwebkit2gtk-4.1-dev`, `libayatana-appindicator3-dev`,
  `librsvg2-dev`, `libxdo-dev`, `libssl-dev`, build tools), then the same
  `npm ci` / `npx tsc --noEmit` / `npm run build` /
  `cargo build --release` recipe.
- `release.yml` Linux job: build the Tauri Linux binary instead of
  `dotnet publish`, stage it where `build-tarball.sh` expects the
  desktop binary, and keep the tarball contents otherwise identical
  (binary + src + web + wheels + install scripts + menu entry).
- `build-tarball.sh` / `install.sh` / `uninstall.sh` /
  `opendrop.desktop.in`: the staged binary is now the Tauri build
  (`opendrop`), installed as the `opendrop-desktop` menu target; the
  script that used to copy the .NET single file (and its
  `libSkiaSharp.so`/`libHarfbBuzzSharp.so` neighbours, noted in
  `install.sh:73`) copies the single Tauri binary instead - no native
  library neighbours any more.
- README Linux requirements gain the runtime libraries
  (`libwebkit2gtk-4.1-0`, `libayatana-appindicator3-1` for the tray).
- `installtests.yml` Linux job: assertions rewritten for the Tauri
  binary (no `libSkiaSharp.so`, no `.so` count): binary present and
  executable, menu entry written, symlink resolves, uninstall leaves the
  data folders intact. **My call:** file-level assertions only - no
  xvfb GUI launch in CI; runtime proof stays on Windows, and the engine
  itself stays covered by the Python suites.

### E. WhatsNew popup ported to React (author: port it)

- A `WhatsNew` component in `desktop/src` styled like the old
  `WhatsNewPopup.axaml` (modal over the main window, dismissible).
- Notes live in a TS module (`src/whatsnew.ts`): FR + EN text for the
  current version, the version key so it shows once per version - same
  "one refusal per version" idea as the update toast, stored in
  localStorage (`opendrop-whatsnew-<version>`).
- The author writes/approves the v1.0.0 note text (it is user-facing
  copy): **I draft FR + EN, he approves before it ships.**
- Release process (README step 3) gains "rewrite `src/whatsnew.ts` for
  the new version" next to the CHANGELOG entry - the Tauri replacement
  for the old `whatsnew.fr.md` bump.

### F. Screenshots retaken from the Tauri app (author: retake now)

- `tools/screenshots/capture.py` currently binds the Avalonia exe
  (`desktop/OpenDrop/bin/Debug/net8.0-windows/OpenDrop.exe`), its window
  title and the `BtnSettings` AutomationId. Re-target it: exe =
  `desktop/src-tauri/target/debug/opendrop.exe` (or the release build),
  window = class `OpenDropWindow` / title from the app, and the UIA
  AutomationIds exposed by the React UI.
- **My call:** add `id=` attributes to the interactive elements the
  capture needs (they surface as UIA AutomationIds through WebView2);
  drive everything with UIA invoke patterns - zero mouse, per the
  author's rules. Shots that cannot be scripted safely (drag-drop of
  real files, for instance) stay the author's: the tool provides a
  "capture now" entry point he triggers with his own hands while the UI
  is in the right state.
- The eleven README images are regenerated in dark + light, same names,
  and `docs/screenshots/README.md` (tooling notes) follows the new
  command line.

## 8. Acceptance criteria

- `desktop/` holds the Tauri app; no `spike` name anywhere user-visible;
  version 1.0.0 consistent across pyproject, main.py banner, tauri.conf,
  Cargo.toml, package.json, .iss.
- The installed Windows app starts the engine on a machine with no
  editable install (venv + PYTHONPATH resolution).
- The updater refuses an installer whose SHA-256 does not match the
  published digest, and a release whose tag is not `vX.Y.Z`.
- Windows setup, portable zip and Linux tarball all carry the Tauri app;
  installtests green (Windows assertions unchanged, Linux assertions
  rewritten for the Tauri binary).
- The WhatsNew popup shows once per version with approved FR + EN text.
- README screenshots show the Tauri app, dark and light.
- README/CONTRIBUTING/SECURITY/CHANGELOG contain no stale Avalonia/.NET
  instruction, and SECURITY's Updates section matches the shipped code.
- The dev app runs from `desktop/` with the engine auto-spawned.
- Nothing committed until the author orders it.
